The Garden

in use

Work with an AI assistant restarts every session — the model arrives knowing nothing about yesterday. Here every project keeps its own memory in three text files. A new session reads them and picks the work up. Twenty projects run on it.

The three files

CLAUDE.md — what this project is and the rules it lives by. Changes rarely; when it changes, something about the project itself has changed.

STATE.md — where the work stands now and what the next step is. Rewritten often, and in meaning: what the work is, not what happened to it.

DECISIONS.md — why things are the way they are. Append-only: a decision that turned out wrong is marked, never deleted, because the reasoning is the part worth keeping.

Nothing here is a framework or a package. The files are ordinary text in the project folder, readable by a person, and the assistant is instructed to read them first and write them last.

What a session does with them

On entry the assistant reads the three files of one project and nothing else. Reading the whole set would cost more and blur the work; a project is meant to be self-contained.

While working anything that settles goes straight into its file, and the assistant says out loud where it put it. This is behaviour, not a command — a command has to be remembered, and remembering is exactly the load being removed.

On the way out the files are rewritten in meaning: what the work now is, what was decided and why. The closing pass is not a backup — nothing is lost without it, because things were filed as they settled.

Decisions

Five, readable without knowing the project.

2026-07-02The person makes no decisions about the process itself

The rituals were exposed as commands to be invoked. That moved the burden of choosing them onto the one person the system exists to unburden. It was inverted: the assistant decides which entry a session needs, files thoughts as they arrive, and offers the closing pass when the signals appear. Nothing has to be requested by name. A missed ritual costs almost nothing, because things are filed as they settle, not at the end.

2026-07-01Filing on the fly is the default; the inbox is only a buffer

Two paths existed for an incoming thought and were being used interchangeably. They were separated. Inside a session a thought goes into its file at once. Away from the desk it goes into a raw inbox and is placed later. The inbox is for when filing on the spot is impossible, not for when it is tedious.

2026-06-30Two sessions cannot silently overwrite each other's file

The design assumed the last writer wins, and a rule — one writer per project — was built on top of that fear. A test showed otherwise. If the file changed on disk after this session read it, the write is refused and the session has to re-read first. Both changes survived. The rule stayed as hygiene, but it is no longer what prevents loss; the tooling is.

2026-06-29The working context stays private even when the code is public

Repository visibility is all-or-nothing, and these files hold unfinished thinking. Where the code is meant to be public, the three files were moved out of that repository into a private one. The rule generalised: a project with public code keeps its context somewhere else, always.

2026-06-29One curator in different modes, not a population of agents

The obvious answer to a growing set of projects is to staff it — a specialised agent per area. Considered and dropped. The pain was visibility and rhythm, and those come from structure: a map, a state file per project, a fixed entry and exit. A fresh agent also starts cold, re-reads everything and breaks the thread of a session that runs across several projects at once. Specialisation now happens as modes of one assistant, and a separate agent is called only for a one-off heavy job.

What the projects actually contain is not published here: several are personal. This page shows the mechanism — the files, the entry and the exit — and nothing from inside them.
